### 2. Testing Philosophy & Principles
```markdown
**Core Principles:**
1. Real Over Mock
   - Unit tests use real Zod schemas (not mock validation)
   - Integration tests make real HTTP calls (not stubbed)
   - E2E tests test real workflows (not smoke tests)
   
2. Test Pyramid Approach
   - Many unit tests (fast, isolated)
   - Fewer integration tests (API contracts)
   - Even fewer E2E tests (critical workflows)
   
3. Defensive Testing
   - E2E tests check element existence before interaction
   - Handle empty states gracefully
   - Clear error messages
   
4. Regression Prevention
   - Automatic baseline tracking
   - Distinguish new tests from regressions
   - Block deployment on true regressions

**Why These Principles:**
- Real code testing catches actual bugs
- Mock-heavy tests create false confidence
- Defensive patterns reduce flakiness
- Regression detection prevents quality erosion
```

### 6. Regression Detection System
```markdown
**Overview:**

The regression detection system automatically identifies when previously passing tests start failing, distinguishing between:
- TRUE REGRESSIONS (was passing, now failing) → Blocks deployment
- NEW TESTS (not in baseline yet) → Informational only
- KNOWN ISSUES (was failing, still failing) → Tracked

**Components:**

1. **Baseline Tracker**
   - File: `test-results/baseline.json`
   - Created: Automatically on first successful test run
   - Updated: Automatically when all tests pass
   - Purpose: Reference point for comparison
   - Contents:
     ```json
     {
       "testResults": [
         {
           "name": "tests/unit/utils/date-utils.test.ts",
           "assertionResults": [
             {
               "title": "should format date correctly",
               "status": "passed",
               "duration": 2
             }
           ]
         }
       ],
       "timestamp": "2026-01-07T12:00:00.000Z",
       "numPassedTests": 436,
       "numFailedTests": 0
     }
     ```

2. **Regression Detector** (regression-detector.cjs - 480 lines)
   
   Functions:
   ```javascript
   loadBaseline()
     → Reads baseline.json
     → Returns baseline test results
   
   loadResults()
     → Reads current test results
     → Returns latest test results
   
   detectRegressions(baseline, current)
     → Compares each test
     → Identifies TRUE regressions
     → Identifies NEW tests
     → Returns categorized results
   
   generateReports(regressions, newTests, failures)
     → Creates REGRESSIONS.md (if any)
     → Creates NEW-FEATURES.md (if any)
     → Creates FAILURES.md (always)
   
   updateBaseline()
     → Replaces baseline.json with current results
     → Only if all tests passing
   ```
   
   Detection Logic:
   ```
   FOR EACH test in current results:
     IF test exists in baseline:
       IF baseline status = "passed" AND current status = "failed":
         → Add to REGRESSIONS (CRITICAL)
       ELSE IF current status = "passed":
         → Add to STILL_PASSING (good)
       ELSE IF current status = "failed":
         → Add to KNOWN_ISSUES (tracked)
     ELSE:
       → Add to NEW_TESTS (informational)
   ```

3. **Report Generator** (generate-report.cjs - 931 lines)
   
   Generates 3 report types:
   
   a) **REGRESSIONS.md** (Critical - Blocks Deployment)
   ```markdown
   # REGRESSIONS DETECTED
   
   **Status: BLOCKS DEPLOYMENT**
   
   The following tests were previously passing but are now failing:
   
   ## 1. tests/unit/modules/recruitment/recruitment-validation.test.ts::should validate email format
   
   - Previous Status: PASSED
   - Current Status: FAILED
   
   **Failure Details:**
   ```
   Expected: true
   Received: false
   
   at line 42:
     expect(result.success).toBe(true);
   ```
   ```
   
   b) **NEW-FEATURES.md** (Informational)
   ```markdown
   # NEW FEATURES DETECTED
   
   The following tests are new (not in baseline):
   
   - tests/unit/modules/training/training-validation.test.ts (15 tests)
   - tests/integration/api/training.test.ts (12 tests)
   - tests/e2e/training-comprehensive.spec.ts (8 tests)
   
   Total: 35 new tests
   
   These are informational only and do not block deployment.
   ```
   
   c) **FAILURES.md** (Actionable)
   ```markdown
   # ALL TEST FAILURES
   
   ## Summary
   - Regressions (Block Deployment): 2
   - Known Failing Tests: 1
   - New Feature Tests Failing: 0
   
   ## Regressions (URGENT)
   [Details of each regression with action items]
   
   ## Known Failing Tests
   [Tests that were already failing - tracked but don't block]
   ```
   
   d) **index.html** (Visual Dashboard)
   - Test count charts

   - Interactive filtering
   - Coverage graphs

4. **Deployment Check** (deployment-check.cjs - 143 lines)
   
   Pre-deployment safety gate:
   ```javascript
   function preDeployCheck() {
     // 1. Check for regressions
     if (fs.existsSync('test-results/REGRESSIONS.md')) {
       console.error('❌ REGRESSIONS DETECTED - BLOCKING DEPLOYMENT');
       console.log(fs.readFileSync('test-results/REGRESSIONS.md', 'utf8'));
       process.exit(1); // Block
     }
     
     // 2. Check pass rate
     const results = JSON.parse(fs.readFileSync('test-results/results.json'));
     const passRate = results.numPassedTests / results.numTotalTests;
     
     if (passRate < 0.95) {
       console.warn('⚠️ Pass rate below 95%:', passRate);
     }
     
     // 3. Check coverage (if enabled)
     const coverage = JSON.parse(fs.readFileSync('coverage/coverage-summary.json'));
     if (coverage.total.lines.pct < 80) {
       console.warn('⚠️ Coverage below 80%:', coverage.total.lines.pct);
     }
     
     console.log('✅ All pre-deployment checks passed');
     process.exit(0); // Allow deployment
   }
   ```

### 8. Design Decisions & Rationale
```markdown
**Decision 1: Real Schemas Over Mocks**

Problem:
- Mock validation creates false positives
- Tests pass but production fails
- Schema changes not caught

Solution:
```typescript
// ✅ GOOD - Real schema
import { insertRecruitmentCandidateSchema } from '@shared/schema';

it('should validate candidate', () => {
  const result = insertRecruitmentCandidateSchema.safeParse(data);
  expect(result.success).toBe(true);
});

// ❌ BAD - Mock validation
function mockValidate(data) {
  return data.firstName && data.lastName; // Incomplete!
}
```

Benefits:
- Tests use actual validation logic
- Schema changes automatically reflected
- Catches validation bugs early
- Production accuracy

---

**Decision 2: Real API Calls Over Stubs**

Problem:
- Stubbed APIs don't test actual endpoints
- Response format changes not caught
- Status code changes not caught

Solution:
```typescript
// ✅ GOOD - Real HTTP request
const response = await fetch('http://localhost:5000/api/crew-members', {
  method: 'POST',
  body: JSON.stringify(data)
});

expect(response.status).toBe(201);
const result = await response.json();

// ❌ BAD - Stubbed API
const mockApi = {
  createCrewMember: () => ({ id: 1, ...data })
};
```

Benefits:
- Tests actual API contract
- Catches endpoint changes
- Verifies response formats
- Integration confidence

---

**Decision 3: Defensive E2E Patterns**

Problem:
- Brittle selectors cause flaky tests
- Timeouts on missing elements
- Poor error messages

Solution:
```typescript
// ✅ GOOD - Defensive
const button = page.getByTestId('button-add');
if (await button.count() > 0) {
  await button.click();
} else {
  console.log('Button not found');
}

// ❌ BAD - Brittle
await page.getByTestId('button-add').click(); // Timeout if missing
```

Benefits:
- Reduces flakiness
- Better error messages
- Easier debugging
- More maintainable

---

**Decision 4: Regression Detection System**

Problem:
- Hard to distinguish new test failures from regressions
- New tests shouldn't block deployment
- Need to track test health over time

Solution:
- Baseline tracking (baseline.json)
- Smart detection (new vs regression)
- Automated reports (REGRESSIONS.md)
- Deployment gating (exit codes)

Benefits:
- TRUE regressions block deployment
- New tests don't block (informational)
- Historical tracking (30 days)
- Automated quality gate

---

**Decision 5: Three-Layer Testing**

Problem:
- Only E2E tests: Too slow, brittle
- Only unit tests: Miss integration bugs
- No strategy: Random coverage

Solution:
```
        E2E (99) - Few, critical workflows
       /
  Integration (114) - API contracts
     /
Unit (223) - Many, fast, isolated
```

Benefits:
- Fast feedback (unit tests run in seconds)
- Comprehensive coverage (all layers)
- Efficient (right test at right level)
- Maintainable (clear separation)
```
